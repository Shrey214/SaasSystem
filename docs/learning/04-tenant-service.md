# Stage 4 — The tenant service

The first running service. Register a business, verify the email, and
platform-admin suspend/reactivate/archive.

**Result:** 72 tests pass (18 domain, 29 BuildingBlocks, 25 integration),
16-step manual flow green, and the service runs both with `dotnet run` and
as a container in Compose.

---

## The bug worth the whole stage

Verify-email returned **500**:

```
DbUpdateConcurrencyException: The database operation was expected to
affect 1 row(s), but actually affected 0 row(s)
```

`version` was `0` in the row and `0` in the WHERE clause, so the optimistic
concurrency token was not the problem. I stopped guessing and turned on EF
command logging, which said everything:

```sql
UPDATE business_status_history SET business_id = @p0, ... WHERE id = @p6;
```

**EF issued an UPDATE for a brand-new row.**

The cause: EF conventionally treats a `Guid` key as `ValueGeneratedOnAdd`.
When it discovers an *untracked* entity hanging off a *tracked* aggregate,
it decides Added-vs-Modified by asking whether the key is already set. Ours
always is — ADR-0010 mints uuid v7 in the constructor precisely so an
aggregate can raise a domain event carrying its own id. So EF concluded the
row must already exist.

What makes this nasty is **when** it appears. Registration worked perfectly,
because the whole object graph went through `Add()` and every node became
`Added`. The bug only fires the first time a child is appended to an
**already-loaded** aggregate — the second use case, not the first. In a
bigger service it would have surfaced a week later in something unrelated.

Fixed once, in `BuildingBlocks`, for all 14 services:

```csharp
entityType.FindProperty(nameof(Entity.Id))?.ValueGenerated = ValueGenerated.Never;
```

That is the honest configuration anyway: these keys *are* generated by us.
`bigint` identity tables (outbox, error_logs, idempotency_keys) don't derive
from `Entity`, so they keep real database generation.

**The lesson:** when the symptom is a row count, read the SQL. I spent two
rounds reasoning about `version` when one log line named the table.

## localhost:5432 was not our container

The service could not authenticate as `hs_tenant_user`, while `psql` inside
the container authenticated fine with the same password.

```
Get-NetTCPConnection -LocalPort 5432 -State Listen
127.0.0.1   proc=postgres        <- postgresql-x64-17, installed locally
0.0.0.0     proc=com.docker.backend
```

Two locally installed PostgreSQL services were running, and one held
`127.0.0.1:5432`, which **wins over Docker's `0.0.0.0` binding** for
anything connecting to `localhost`. The app was talking to a completely
different database that had never heard of our roles.

The error message — `password authentication failed for user
"hs_tenant_user"` — points at credentials, which is exactly the wrong place
to look.

Container moved to **5433** on the host. Local installs untouched: they are
the user's machine and may be needed for work.

This also exposed a blind spot in Stage 2's verification.
`verify-isolation.ps1` runs `psql` *inside* the container, so it correctly
tested the container's PostgreSQL — and would have passed identically while
every host-side connection went somewhere else. A test that runs on the
wrong side of the boundary it is checking can be green and meaningless.

## Four smaller things, each real

**`Max Pool Size` is a SqlClient keyword.** Npgsql calls it
`Maximum Pool Size`, and the wrong one throws at startup with
`Couldn't set max pool size`. Mildly embarrassing given Stage 2 raised
`max_connections` specifically because of connection-pool sizing.

**A non-nullable `int` query parameter is REQUIRED in minimal APIs.**
`GET /me/status-history` with no `?limit=` threw
`BadHttpRequestException` before the handler ran. It was latent on the
platform search endpoint too — that one only looked fine because the manual
test happened to pass `?limit=3`. Now `int? limit` with a default, and a
regression test on each.

**`EFCore.Relational` was on a different build to `EFCore`.** The Npgsql
provider (10.0.3) asks for Relational 10.0.4 while EFCore was pinned to
10.0.11, and `MSB3277` failed the build. Transitive pinning can only align a
package that has a `PackageVersion` entry, so Relational now has one even
though nothing references it directly.

**Two validation shapes in one service.** The suspend endpoint used
`Results.ValidationProblem`, which emits no `code`, PascalCase field names
and a different `type` URI — while everything else went through
`ProblemDetailsFactory`. `docs/00-conventions.md` §5 says no service invents
its own error shape, and two shapes inside one service is that same problem
in miniature. The helper now lives in `BuildingBlocks.Web` so all 14 share
it, with a regression test.

## The container build was stricter than the local one

`docker build` failed on analyzer findings **inside EF's generated
migration** — `CA1861`, `CA1825` — while `dotnet build` had been clean all
along.

`.editorconfig` is what marks `**/Migrations/*.cs` as generated code and
switches analysis off for it, and I had not copied it into the build
context. So the container saw a stricter ruleset than the developer machine.

This is the worst shape of build failure: green locally, red in CI, with no
visible reason. `.editorconfig` is now copied explicitly, with a comment
saying why it is not optional.

## Things settled by deciding, not discovering

**Who activates a business?** `Goal/Domain.txt` Part 1 lists
*"Business Activation | Platform Admin"*, which reads like every signup
waits for a human. But its **business rule** column says *"suspended
businesses cannot use platform"* — so that row is about **un-suspending**,
not vetting. Confirmed with the user: registration is self-service, and
`Activate` only moves `Suspended → Active`. Workflow A in the same document
agrees, running straight from Register → Verify → Choose Subscription with
no approval step.

**`businesses` has no `tenant_id`.** The one main table in the system with
no tenant filter, because the row does not belong to a tenant — its `id`
*is* the tenant id the other 13 services store. So `Business` deliberately
does not implement `ITenantScoped`, and this service's isolation test had
to be written differently: it proves the `/me` endpoints are scoped to the
caller and cannot be aimed elsewhere.

**Duplicate email returns 409.** Asked, because it leaks which businesses
exist. The user first chose to hide it, which would have forced `202
Accepted` with no id in the response and moved verification to a
token-only route — then reverted to `409`. Recorded because the reversal
saved a structural change, not just a status code.

**Email normalised to lowercase on write.** I first wrote a unique index
named `ux_businesses_owner_email_lower`, then noticed the fluent API cannot
express a functional index on `lower(owner_email)`. Rather than hand-write
SQL in a migration, the column is normalised on write so a plain unique
index gives case-insensitive uniqueness. `Owner@x.com` and `owner@x.com`
are the same mailbox to every mail server; the cost is that original casing
is not preserved, which nobody has needed.

## The uniqueness guard is the index, not the check

`RegisterBusinessHandler` does `EmailExistsAsync` before inserting. That
`SELECT` is a **courtesy**, not the guard — two simultaneous requests both
pass it. Only the unique index is atomic, so the handler catches
`SqlState 23505` and turns it into the same `409`.

`Register_ConcurrentRequestsForTheSameEmail_ProduceExactlyOneBusiness`
fires eight parallel registrations and asserts **1 created, 7 conflicted,
one row in the table**. It passes — but it passes because of the index. This
is a small rehearsal for Stage 10, where the same lesson costs a lot more
if it has not been learned.

The `SqlState` check is done by reflection so `Application` stays free of a
reference to Npgsql. Slightly ugly; the alternative is leaking the data
provider into the layer that is supposed to not know about it.

## The outbox is doing nothing, on purpose

Every lifecycle change writes an `outbox_messages` row in the **same
transaction** as the business change, and all of them sit unpublished:

```
 id | event_type                    | unpublished
----+-------------------------------+-------------
  1 | tenant.business.registered.v1 | t
  2 | tenant.business.activated.v1  | t
  3 | tenant.business.suspended.v1  | t
```

There is no RabbitMQ until Stage 7. ADR-0006 says a missing broker means
rows accumulate and users keep working, so this is the design running, not
a gap. By Stage 7 there will be three stages of backlog to drain — which is
a better test of the publisher than anything synthetic.

## Still temporary

`X-Tenant-Id` is a forgeable header, enabled **only** in Development. A
deployed instance gets no tenant rather than a fake one, so it cannot
quietly survive. Stage 5 issues real tokens, and the claims path is already
written and tried first — so that change deletes code rather than altering
behaviour.
