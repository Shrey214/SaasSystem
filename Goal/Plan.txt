WHERE WE START
--------------

STAGE 1 = Phase 3-5 design docs. Not tables, not code.

Reason: table design IS boundary design. A bookings table with a foreign
key to rooms silently decides that Booking and Property share a database.
Deciding boundaries first costs one stage; getting it wrong costs a
rewrite of every service.

After that, DB design and code proceed ONE SERVICE AT A TIME — each
service fully finished (design -> tables -> migration -> endpoints ->
tests -> compose -> commit) before the next one starts.

KEY DECISION — AVAILABILITY LIVES INSIDE BOOKING

  availability = sellable inventory
                 - (confirmed bookings + active holds + blocks)

A separate Availability service would force a DISTRIBUTED TRANSACTION ON
THE HOTTEST, MOST RACE-PRONE PATH in the whole system (every hold and
every booking).

Instead: booking owns the availability ledger and maintains its own
inventory projection built from property events. A Redis read model is
added at Stage 13 for search fan-out.

Recorded as an ADR with the rejected alternative — this is exactly the
kind of call you are trying to learn to make.


DATA OWNERSHIP RULES

  DATABASE-PER-SERVICE
    One local Postgres container, one database each
    (hs_tenant, hs_property, ...).
    No cross-database queries. No cross-service foreign keys.

  TENANT ISOLATION — THREE LAYERS
    1. tenant_id comes from the JWT via ITenantContext,
       NEVER from a request body
    2. EF Core global query filter on every tenant-scoped entity
    3. Postgres RLS on hot tables later, as defence-in-depth
    Every service test suite gets a
    "tenant A cannot read tenant B" test.

  CROSS-SERVICE DATA
    Replicate the minimum via events.
    Snapshot immutable facts into the owning aggregate
    (price snapshot on the booking, guest name on the booking room).

  CONVENTIONS
    uuid v7 primary keys (time-ordered, collision-free across services)
    numeric(18,4) + ISO currency for money — never float
    timestamptz for instants,
      but DATE for stay nights (a hotel night is a date, not an instant)

  EVERY SERVICE
    a transactional outbox table
    an idempotency_keys table for every externally-triggered write

AUTH DESIGN (replaces Keycloak)
-------------------------------

  ISSUER
    The identity service is the only token issuer.
    ASP.NET Core Identity  -> user store, password hashing, lockout,
                              email/phone confirmation, 2FA later
    Our own token endpoint -> POST /auth/login, /auth/refresh,
                              /auth/logout
    RS256 signing          -> private key in the identity service only,
                              public key published at
                              /.well-known/jwks.json

  ACCESS TOKEN CLAIMS
    sub            user id
    tenant_id      the business (absent for platform admins)
    scope_type     platform | tenant | property
    roles          role codes
    perms          permission codes (or a version stamp, see below)
    props          authorized property ids
    jti, exp       short-lived: 10-15 minutes

  REFRESH TOKENS
    Rotating, stored hashed in the identity DB, one row per device,
    revocable. This is what makes "Remove Staff Access" actually work
    (Domain.txt Part 1 + Part 18) — access dies within one token
    lifetime, refresh dies immediately.

  VALIDATION — WHERE IT HAPPENS
    Each service validates the JWT itself with AddJwtBearer pointing at
    the identity service JWKS (cached, auto-rotating). Kong OSS does
    routing, rate limiting and a coarse signature check; it does NOT
    become the only line of defence, because a service must never trust
    a caller just because it came through the gateway.

  THE PROBLEM WE ARE DELIBERATELY BUYING
    Permissions and property access now live in a token, so they go
    stale the moment an admin revokes them. Stage 5 solves it and
    documents the trade-off:
      - short access-token lifetime
      - a perms_version claim checked against a Redis/DB value
        (Redis arrives Stage 13; DB check until then)
      - immediate refresh-token revocation
    This is the same staleness problem an external IdP would have
    given us — we now own both sides of it, which is better for
    learning.

  IF REAL OIDC IS EVER NEEDED
    (third-party apps, channel managers, social login on the public
    property website) -> add OpenIddict, which is free/MIT and runs
    inside the same .NET identity service. Not now.

IDEA PARKING LOT (revisit after Stage 19)
- - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - -

Rule: ML earns its place only where a HUMAN DECISION is currently made
on a guess. Three features, not a shelf of them. Everything is a
SUGGESTION a human accepts or rejects — nothing writes a rate, blocks a
room, or takes money on its own.

Second rule: ML needs history. Nothing is trained until Stages 4-19 have
been running and generating events. Stage 1 only makes sure the events
carry the right fields.


THE THREE FEATURES

  ML-1  CANCELLATION / NO-SHOW RISK SCORE            (the unique one)
        At booking confirmation, score 0-1: how likely is this booking
        to cancel or no-show?
        Features: lead time, length of stay, rate plan (refundable?),
                  deposit taken, channel (web / walk-in / phone),
                  weekday vs weekend arrival, guest stay history,
                  season, price vs property average.
        What it unlocks — real decisions a hotel actually makes:
                  - require a deposit on high-risk bookings
                  - allow controlled overbooking on high-risk dates
                  - prioritise which arrivals reception should confirm
        Model: LightGBM binary classifier (ML.NET).
        Why unique: almost nobody builds this into a small PMS, and it
        turns two existing capabilities (no-show processing,
        cancellation policy) from reactive into predictive.

  ML-2  DEMAND FORECAST -> RATE SUGGESTION
        Per room type, next 60-90 days: forecast occupancy, then
        suggest a rate nudge with a reason.
        e.g. "Deluxe, 12 Oct: pace is 40% above the same lead time
              last year -> suggest 3,000 -> 3,400"
        Features: booking pace by lead time, historical occupancy,
                  day of week, season, local events (manual calendar),
                  current pickup vs same-time-last-year.
        Model: SSA time-series forecast (ML.NET) for occupancy, then a
               transparent rule layer for the rate delta — so the
               manager always sees WHY.
        Hard limits: writes to a suggestions table only. A manager
               accepts it and THEN pricing changes. Accept/reject is
               stored and becomes training feedback.

  ML-3  REVIEW ASPECT + MODERATION ASSIST
        On review submission, extract aspect sentiment
        (cleanliness / staff / location / value / facilities) and flag
        abusive or spam text for the existing moderation step.
        Model: ML.NET text featurization + multiclass classifier;
               swappable for a local ONNX sentiment model.
        Why: the moderation capability already exists in the blueprint
        (Domain.txt Part 16) and is pure manual work today.

  BONUS (not really ML, cheap, do it at Stage 9)
        Duplicate guest detection — fuzzy match on name + phone +
        email + document number, so the same guest is not created five
        times. Trigram/Levenshtein in Postgres, no model needed.

ARCHITECTURE

  ONE SERVICE: intelligence (.NET 10 + ML.NET). No Python container,
  no paid API, nothing to pay for. ONNX Runtime is the escape hatch if
  a model ever outgrows ML.NET — train elsewhere, export .onnx, keep
  inference in .NET.

  IT OWNS ITS OWN DATABASE, like every other service. It builds a
  feature store by consuming RabbitMQ events (BookingConfirmed,
  BookingCancelled, NoShowRecorded, CheckedIn, CheckedOut,
  NightlyOccupancySnapshot, ReviewSubmitted). It never queries another
  service's database.

  IT IS NEVER IN THE HOT PATH. Booking does not wait on a score.
    - ML-1 scores are written back as an event, and booking stores the
      score as an attribute it can ignore
    - ML-2 writes suggestions, read on demand by a manager
    - ML-3 runs after the review is already saved
    No score available -> the system behaves exactly as it does today.
    That degradation path is a Stage 21 chaos test.

  TRAINING runs as a scheduled background job inside the service,
  writes a versioned model file + its metrics, and never blocks
  serving. Model version is recorded on every score so a bad model can
  be traced and rolled back.


THE GENUINELY HARD PART — MULTI-TENANT ML  (this is the learning)

  A new property has 40 bookings. A per-tenant model is worthless.
  One pooled model across all tenants leaks one business's demand
  patterns into another's pricing advice.

  Our answer, recorded as ADR-0006:
    1. COLD START      < N bookings -> no model, transparent heuristic
                       (rate plan + lead time buckets). The UI says
                       "based on rules, not enough history yet".
    2. POOLED MODEL    trained on tenant-anonymised features only —
                       never tenant_id, property name, or any
                       identifier as a feature.
    3. TENANT CALIBRATION  a small per-tenant correction layer on top
                       once history exists.
    4. NEVER CROSS-TENANT OUTPUT  a suggestion for tenant A may cite
                       only tenant A's own numbers as its reason.

  Also: POINT-IN-TIME CORRECTNESS. Training rows must contain only what
  was knowable at prediction time. If "was_cancelled" or the final
  occupancy leaks into the features, the model looks brilliant offline
  and useless live. The feature store is therefore event-sourced with
  an as-of timestamp on every row — which is exactly why intelligence
  comes after reporting (Stage 17) rather than early.
